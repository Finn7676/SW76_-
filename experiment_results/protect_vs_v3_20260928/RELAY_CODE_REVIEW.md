# Relay 冻结源码独立审查

日期：2026-09-28。对象：`tyhh_test/tyhh_qos_protect_relay/main.cpp`。

源码 SHA256：`c65cfa425e09b38662610fd19fc309b419e5c82edc2c6e7cddadeab8337b4961`。审查前后均与 `relay_final/sources/0/tyhh_qos_protect_relay/main.cpp` 一致。本次未读取开发或最终比赛的 `results.csv`、`summary.json`，未运行对战，也未修改候选源码。以下判断仅依据源码和独立断言；不能据此推断胜率提升。

## 结论与适用范围

在合法地图输入、正尺寸且宽高不超过 64、当前 500 轮对局，以及内部 `portalKeys` 由已验证坐标构造的条件下，未发现新增的可复现崩溃或越界路径。独立 AddressSanitizer/UndefinedBehaviorSanitizer 检查通过，包括边界坐标、最大门户 ID、房间容量边界、协议分派和 20,000 个任意 64 位消息探测。该检查不是形式化证明，也未覆盖整个 bot 的所有执行路径。

需保留的主要局限有两类：旧 32 位接收分支仍可能污染地图；房间声明和定向消息仍是局部、短期信息，不是全队一致的锁或可信身份认证。另发现 736–739 轮状态消息被错误分派的潜在扩展问题，超出本次 500 轮验证范围。没有依据这些问题修改冻结实验。

## 已核实的协议边界

1. **完整门户对的位布局自洽。** 四个坐标各 6 位，门户 ID 13 位，方向 1 位，保留位 1 位，队伍 1 位，类型 8 位，校验 16 位，共 64 位。发送端只接受两个同方向、同 ID 的规范端点，ID 范围为 0–8191；接收端先检查校验、队伍、保留位和坐标范围，再形成数组下标。坐标 `(63,63)` 与 ID `8191` 的往返断言通过。见 `main.cpp:287–318`。

2. **门户对接收在写入前检查两端。** 已知非门户地形、不同门户 ID、额外冲突端点、端点顺序不合法均拒绝。两个端点通过检查后才调用 `setEdge`，重复收到同一消息不会增加重复端点。已有测试覆盖校验破坏、不同队伍、已知海带冲突和第三端点冲突。

3. **旧单端格式的发送容量修复正确。** 13 位 payload 中还要放 1 位方向，实际只能承载 12 位 ID；`chooseMessage()` 将单端发送限制为 ID `<4096`。更大的 ID 仅在完整双端已知后通过独立门户对消息传播。未知另一端时，不能提前广播可用完整连接，这是明确的信息限制。见 `main.cpp:419–425`。

4. **四方向发送没有同方向覆盖。** `slot = (d-base+4)&3` 对四个方向是一一映射；普通消息、门户对、房间声明、队友状态分别占用不同可用槽位，缺失槽位回退为普通消息。房间声明不再独占四个方向。状态和声明仅在动作投影落点已知且投影存活时生成；未知门户出口不产生虚构落点。见 `main.cpp:1321–1336`。

5. **状态消息仍需当前视野核验。** ID 行动顺序约束发送轮次，收到的信息还要与可见己方头的位置和 ID 匹配，才能提高队友长度估计。正常 0–499 轮状态消息均可通过真实 `receive()` 分派；独立断言逐轮覆盖。见 `main.cpp:248–273`。

## 具体问题与局限

### 旧 32 位兼容分支仍可覆盖已知地形

`receive()` 对裸 32 位报文不要求队伍或格式标记，只检查原有 4 位 tag。`M_PORTAL` 分支只检查目标当前不是 `E_PORTAL`，随后会把已知 `E_KELP` 或 `E_OPEN` 改写为门户。独立断言已复现：在已知海带边上输入 tag 正确的裸单端消息，该边被改写为门户。见 `main.cpp:368–391`。

这是保留的旧协议接收路径，与新增完整门户对的严格冲突校验不同。新包装报文带队伍标记，并不意味着所有被接受的信息都有队伍隔离；`main.cpp:277–278` 的注释表述过宽。普通对手消息碰巧采用兼容旧格式、消息来源不可信，或旧消息与当前已知地图冲突时，存在错误拓扑传播风险。当前断言没有触发越界，但错误地形会影响寻路和后续房间判定。此事实不能直接作为本轮对战失败的原因。

建议后续独立实验：明确旧格式接收的兼容需求；若保留，应对单端拓扑采用与双端一致的已知地形冲突策略。本次保持冻结源码。

### 声呐标记不是身份认证，声明不具备所有权

队伍位和校验能筛掉不匹配格式及一般损坏，不能证明消息确由己方发送。房间声明没有发送者 ID、发送时间或所有者选择规则；接收时以本地当前轮重置有效期，最后一次接收后最多再保留六轮。多个龙可以同时宣称同一房间；离开或死亡后也没有主动撤销。门户 ID 标识连接的两端，并不区分“占用哪一端的房间”。见 `main.cpp:392–403,442–446`。

因此声明是短时的入口抑制信号，不能称为排他锁、完整去重机制或确认仍在房间中的证明。动作投影也不是下一轮的真实存活确认。

### 房间判定只证明局部几何和资源记录

`provenResourceRoom()` 仅沿已知普通边展开，未知边即拒绝；以规范门户边为边界，同一门户 ID 但两条不同边也拒绝；最多 24 格，且至少一格存在有限 `pearlDue`。独立断言确认 24 格允许、25 格拒绝，以及同 ID 不同边界拒绝。见 `main.cpp:329–357`。

该判定不要求房内只有一条龙，不比较资源数量、刷新时间、房间承载能力或门户另一端价值；资源记录也没有新鲜度门槛。周期图中的环路允许存在，故它与 V3 的无环小口袋判定不是同一个概念。已知资源源并不等于当前有珍珠，也不等于独占可以提高收益。

本龙位于房间内时，普通评分的声明过滤有 `occupiedPortalId` 例外，因此并非永久禁止本龙离开；但前 80 轮的强制门户分支没有该例外，会跳过自己所属房间的门户。该行为只能作为具体策略差异描述。见 `main.cpp:943–959,1112–1113`。

### 消息可达性和覆盖率没有保证

每种可用信息仅保留一个旋转方向，接收仍依赖声呐的实际可达性；这不是每轮向全队广播。与基线给状态最多三个空闲方向相比，全部类别同时可用时状态只占一个方向。门户对轮播遍历 `portalKeys`，一个门户通常含两个端点，所以同一对在一轮完整遍历中可能发送两次；没有按新信息或紧急性排序，也没有确认收包机制。它共享的是拓扑，不是已探索状态或 Scout 任务声明。

### 736–739 轮状态消息分派冲突（不在当前测试范围）

状态格式的位 40–47 来自 `ROUND >> 2`；当轮数为 736–739 时该字节等于 `0xB8`。接收函数在状态解码之前按该字节识别门户对，并无条件 `continue`，导致合法状态消息被丢弃。独立断言已复现轮 736：`decodeStatus()` 本可通过，经过 `receive()` 后状态列表为空。见 `main.cpp:250–258,364–366`。

当前 0–499 轮不会出现该碰撞，不能据此否定本次 500 轮实验；若将来延长局数，需修正分派或限定协议轮数范围。其他字段也有固定容量：状态轮次 10 位、ID 16 位、长度 10 位，旧珍珠/敌情轮次只有 9 位。

### 保留的旧敌情长度截断

敌情 payload 共 13 位，其中轮次占 9 位，只剩 4 位长度；发送端却截断至 31 再移位。长度 16–31 因 payload 掩码变为 0–15。此为基线保留问题，非 relay 新引入，当前 `FEAT_HUNT_SIGHTINGS=0` 也限制了它对追猎规则的影响。它仍不应被描述为完整敌方长度传播。见 `main.cpp:233–235,386,414`。

## 验证记录

新增独立审查程序：`relay_review_checks.cpp.txt`，只包含并调用冻结 bot 的真实实现，没有在测试中重新实现协议。编译并执行命令：

```sh
clang++ -std=c++20 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -x c++ experiment_results/protect_vs_v3_20260928/relay_review_checks.cpp.txt -o /tmp/tyhh-relay-review-checks
ASAN_OPTIONS=detect_leaks=0 /tmp/tyhh-relay-review-checks
```

结果：边界断言和 20,000 个任意报文探测通过，无 ASan/UBSan 报错；同时确认旧格式地形覆盖和超范围轮次分派问题。测试通过重命名 `main` 包含源码，编译器对未被调用的重命名入口给出缺少返回语句警告；该警告不是测试运行的内存错误。LSan 因沙箱环境关闭。最终候选源文件哈希未变化。

审查结论是“在声明边界内未复现新增内存安全故障，并存在以上协议与策略局限”，不是“必然更强”或“已证明能击败 V3”。胜负结论必须单独由冻结后的配对比赛产生。
